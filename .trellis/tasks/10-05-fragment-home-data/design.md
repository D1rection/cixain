# 设计：补齐碎片详情的文章元数据

## 根因与数据流

`scripts/static-renderer.js` 为每个路由写入 `__BLOG_DATA__`。文章详情已有全量 `posts: posts.map(metaOnly)`，碎片详情只有当前 `fragment` 和 `fragments`。`src/main.jsx` 首次加载时解析 JSON，作为固定的 `BlogDataContext.Provider` 值；wouter 站内导航只切换组件，不加载目标静态 HTML 或更新该值。

因此碎片首屏正常，返回首页后 `Home` 和 `Sidebar` 的 `posts = []` 回退使列表及统计为空。刷新会加载首页自己的完整数据。开发入口直接导入全量文章元数据，容易掩盖生产路径缺陷。

## 推荐变更

在 `static-renderer.js` 的碎片路由 `data` 内增加：

```js
posts: posts.map(metaOnly),
```

生产文章发布集合 → `metaOnly` → 碎片 HTML 的 JSON → 首屏共享上下文 → 首页、侧栏及其他文章列表消费者。正文依然按页分发，只有当前碎片正文内联，进入文章详情沿用已有正文按需加载。

修复边界是构建层的一处缺失字段，与文章详情现行策略一致。无需修改首页、侧栏、浏览器入口、路由或碎片请求逻辑。保持发布集合原顺序，不预先按首页可见性筛选，否则分类与归档会不完整。

## 契约与兼容性

- 碎片详情的 `posts` 与首页集合及顺序一致，来源为生产发布集合，而非 dev 集合或反向引用。
- 使用现有 `metaOnly` 排除正文和交互数据；当前 `fragment.fragmentContent` 不剥离。原页面字段及 URL 不变。
- 新字段兼容当前消费者，不新增加载态或网络往返。验收记录实际 JSON 字节增量，确认新增仅为元数据。
- 必须重新生成并部署静态页面；仅更新客户端脚本无法补齐旧 HTML 数据。

## 取舍与范围

元数据注入符合现有 SSG 规范。导航时请求全站数据会改变架构并违反质量约定；将首页链接改成整页刷新只能规避触发条件；全路由加载器重构超出本次范围。

代码检查发现分类、标签、系列静态页的 `posts` 为筛选子集，可能导致这些页面首次加载后返回首页列表不完整；这是尚未浏览器复现的推断，另行评估。

## 验证与回滚

以生产产物和真实站内导航作为主要证据，不能只验 dev。步骤见 `implement.md`。预计实现只改 `static-renderer.js`，同时在 SSG 规范记录数据契约。回滚时撤销本任务字段与规范更新、重新构建；回滚会恢复原缺陷。
